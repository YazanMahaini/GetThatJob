# SetupSkill

Use only when the selected applicant workspace lacks `.getthatjob/setup.json`. First use is **per workspace**, not once per plugin installation; otherwise one person's setup would prevent another person's workspace from being created. Do not run against the plugin source.

Choose the workspace by the explicit user path when provided. Otherwise use an empty or clearly designated job-search current workspace; if the current directory is an unrelated project, create a `GetThatJob` sibling. Tell the user the path. Before running the setup helper, handle the first-use email and submission choices below. Resolve `../../scripts/setup_workspace.py` relative to this SKILL.md. For a workspace that already contains applicant files, run `--workspace <path> --dry-run` first, inspect the proposed additions, then run with `--workspace <path>` only when the list contains missing scaffold files and the marker. The script creates `applications/`, `CoverLetters/Template/`, `CVs/`, `Qualifications&Certificates/`, `APPLICATION_PROFILE.md`, other workflow Markdown files, `APPLICATIONS.csv`, and the one-time marker. It uses exclusive file creation: an existing file is never overwritten or truncated, including when another process creates it during setup. Do not remove, reset, or reformat existing applicant files or directories to make setup pass. If Python is unavailable, create the same files from `../../assets/workspace/` with local file tools, copying only absent files, then write `.getthatjob/setup.json` only if absent.

As soon as you confirm the marker is absent, inspect existing workspace instructions for an email plugin or provider. Reuse a recorded choice. Otherwise ask: "Which email plugin should I use to check application confirmations? Please select it with `@`, such as `@Outlook Email` or `@Gmail`." Ask before writing the marker, then continue independent setup while the answer is pending. Resolve the selected `@` mention to the actual Codex plugin name or ID and inspect its read-only search tools; do not assume Outlook because the creator uses it. If the applicant only names a provider, use its plugin only when the match is unambiguous; otherwise ask them to select the exact plugin mention during this first-setup exchange. If the selected plugin is not installed or connected, explain how to add or connect it and continue independent setup and job-search work. Do not request or store passwords, one-time codes, or mailbox contents. Record the selected plugin name or ID in the private `OPERATIONS.md` under **Confirmation email plugin**, replacing the template placeholder if newly created or adding a short section without changing unrelated existing text. If the applicant declines or has not answered, record `Not configured` and explain that email receipt checks will remain unavailable until they explicitly choose a plugin. Ask this choice once per applicant workspace; a later run with `.getthatjob/setup.json` is a resumption and must not ask again. A later explicit request to change the selected plugin may update `OPERATIONS.md`.

During the same first setup, ask before writing the marker: "Should I stop after filling and checking each application so you can click Apply yourself or tell me to submit that specific application, or submit complete applications automatically without asking you each time? The default is to stop and let you click Apply." Inspect any existing workspace instructions first and preserve a recorded submission choice. Save `stop-and-wait` by default, including when the applicant has not answered; save `automatic-submit` only when they explicitly choose it. Record the mode in the private `OPERATIONS.md` under **Submission preference**, without replacing unrelated text. `automatic-submit` is standing authorization for the final Apply/Submit control after all application checks pass; it does not authorize an e-signature, a signature-equivalent declaration, a fee, or an unknown fact. A later run with the setup marker reads this mode and does not ask again. The mode stays in effect until the applicant explicitly changes it, including in an active request.

Then run [SetupChecker](../setup-checker/SKILL.md); it routes any CVs already present through [ProfileIntake](../profile-intake/SKILL.md) once. During initial setup, if multiple approved CVs have different visual designs and no style choice is recorded, ask the applicant to choose one of **their own** CVs as the design reference. Record only its filename in private `CV_INDEX.md`. If CVs arrive later, make the same conditional choice during intake rather than rerunning setup. The design choice never determines which CVs provide factual information. Report the specific documents and profile inputs the user should add. An empty cover-letter template or credential folder does not prevent setup. Never copy the creator's CVs, letter design, identity, country, or role preferences into the new workspace.
